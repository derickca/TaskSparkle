# Changelog

What each release of TaskSparkle carries, in plain words. The shape follows Keep a Changelog. Versions follow `vMAJOR.MINOR.PATCH`. Each release is tagged in git. Each release is also published as a GitHub release.

Inside a release, the app stamps every deploy with a build stamp. The stamp is `rYYYY-MM-DD-N`: the date and a counter for the day. The release names the code a person can pin. The build stamp names the exact deploy they run. A bug report that gives both pins the problem down in full.

## [Unreleased]

The Feedback page no longer posts to a named outside service out of the product's own files: a deployment names its feedback target in its own settings — the `FEEDBACK_URL` var on Cloudflare, `feedbackUrl` in a home copy's config — and a copy with no target named shows no Feedback page and no Feedback link anywhere. Where a target stands, the form posts to the app's own API, which passes the note to the target from the server side and relays its answer. Build r2026-11-07-3.

## [1.0.0] - 2026-11-04

TaskSparkle is a personal kanban board: boards, columns, cards, labels and projects for one person's work, with agent keys so an AI agent can hold a card's next step alongside you. It runs as one small app — host it on Cloudflare, or run it on your own machine. This is the first public release; everything in this release is what the app carries at launch.

### Fixed

- Two editor faults are fixed. Changing a card's Next step could look as if it had not taken: a refresh that had set out before the change could land after it and repaint the editor from the older state, so the chooser showed the previous holder again until the next refresh — the saved step never changed back, only the display did. The same late refresh could also stop a Close press: it rewound what the editor remembered of the server's card, so closing asked about a change that had never happened and the editor stayed open for a second press. A snapshot older than the state already on show is now refused and fetched again, a write's answer moves the shown version with it, and a hand-over still in flight holds its painted step across a state swap. Build r2026-11-04-3.

  - As a faded background on the card's face
  - As a thick trim around the card
  - As a thick band across its top
- Set the mode per board in Settings → Boards. It paints the board's card faces and its phone overview. The overview uses thinner lines.
- The mode never touches the card editor, the schedule, search results or the archived list. Build r2026-10-29-1.

### Removed

- The project colour. Projects now carry a name and an icon only.
- The coloured dot no longer shows anywhere. The colour picker is gone from Settings → Projects.

## [0.1.0] - 2026-10-29

The first tagged release. The work below was built and hardened across build stamps r2026-10-26 to r2026-10-28-6. This list groups the work by theme, not by deploy.

### Added

- Boards, columns and cards that are fully the owner's own. Owners can add, rename, re-icon and remove boards, columns, labels and projects. Cards move between columns and boards. A board can be copied.
- Cards with checklists, links and comments. Steps can be reordered, and the count shows on the card face. A card can wear more than one label. It can also carry a project, a due date with a Late tag and an Important flag.
- New ways to see the work. A Schedule view shows dated cards. Search checks titles, notes and steps. A phone overview shows every column at once. Each board has an Archived list. Named looks have light and dark palettes.
- An installable app. TaskSparkle installs on a phone like an app. It remembers each board as it was left. Open boards update live when a change lands elsewhere.
- A second way to run it. The self-host server serves the same app and API. It uses one Node process and one SQLite file on your own machine. It sits beside the Cloudflare deployment.
- The agent API. Each agent key is personal, named and revocable. All keys can live at once. Cards and comments carry a stamp that names the key that made them. The API serves its own directions. An agent can start at the door and learn the rules from the service itself.
- A change watch. The version counter, the state answers and the creator stamps let a person or an agent follow what changed. They also show whose work it was. `docs/watching-for-changes.md` explains it, and `examples/change-digest/` runs it.
- Erasure. A person can delete their boards and account in one act from Settings. A self-host operator can erase a person who cannot sign in.
- The contributor scaffolding. It holds `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` and `SECURITY.md`. It also holds issue and pull request templates, plus checks on every pull request.

### Changed

- The self-host sign-in is now per person. Each person sets a password through a one-use invite link. This replaces the one shared household password of the first self-host build.
- Nightly backup exports are now kept for 14 days, not 35. The README and the workflow now say in plain words what one export holds.
- Agent keys no longer see the change stamp or the owner's email in their answers. The person's own door keeps both.

### Security

- Two adversarial review rounds, plus a fresh-eyes security and privacy review. Each finding was fixed or recorded.
- The allowlist is checked on every request at both doors.
- A key can never manage keys.
- Writes are judged before they land.
- Sizes are capped.
- Multi-step changes land as one batch.
- Browser security headers guard the app pages in both deployments. They include a content security policy. The app runs under it with no exceptions.
- Self-host hardening:
  - A sign-in page that names nobody
  - Throttled password attempts
  - Passwords stored only as salted hashes
  - Caps on request bodies and socket frames
  - An option to bind the server to its own machine only
